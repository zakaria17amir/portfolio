Overview

A personal finance tracker you run yourself: accounts, transactions, per-category budgets, filtered reports, and accounts shared with a partner or housemate. It started as a semester project and I kept building on it because I wanted to actually use it.

The problem

Most budgeting apps want bank credentials and a subscription in exchange for a dashboard. FinTrack takes the opposite trade: a small application backed by a single SQLite file you can copy, back up, or delete, with nothing leaving the machine it runs on. The cost of that choice is that every feature a hosted service gives you for free — sharing, permissions, oversight — has to be built and enforced here.

The data

Five domain tables on top of Laravel's defaults: accounts, transactions, categories, budgets, and the pivot that joins users to accounts. That pivot is where the interesting part lives. A joint account is not "two users see the same rows" — one person may own it while another is only allowed to look at it, so the permission level is an attribute of the relationship rather than of either side. Balances are maintained as transactions are created, edited and deleted, so the account row and its transaction history never have to be reconciled by hand.

Approach

  • Modelled sharing as a many-to-many with a permission level on the pivot, and made that single fact the source of every authorization decision in the app.
  • Enforced permissions server-side on every route. The interface hides what you cannot do, but hiding is never what stops you — the check runs again on the request.
  • Built reports as composable filters — date range, multiple categories — over spending by category, a six-month income-versus-expense trend, and a breakdown table.
  • Gated the admin panel behind role middleware and kept it deliberately narrow: account and category management, and read-only oversight of transactions.

Results

A working self-hosted application with budgets, reports and shared accounts, set up from a clone in about six commands, with PHPUnit tests and a CI workflow running on every push. The authorization model is the part I would defend in an interview: it is the reason the feature set stayed small and the rules stayed in one place.

What I would do differently

  • Balances are updated imperatively on every transaction write. That is fast to read and easy to get wrong — a missed edge case in one code path leaves the stored balance disagreeing with its own transactions. A derived balance with a cached snapshot would be harder to corrupt.
  • Recurring transactions are stored as an interval on the transaction, not as a schedule that materialises entries. That works for display and not for forecasting, which is the feature people actually want next.
  • The seeded demo accounts use a well-known password. That is right for a local demo and exactly the kind of thing that survives into a deployment it should not — it belongs behind a flag, not behind a warning in the README.
  • Tests cover the authorization paths well and the reporting maths thinly. The reports are where a silent wrong number would do the most damage.

Tech stack

Laravel 13 on PHP 8.4 with Breeze for authentication, Eloquent policies and role middleware for access control, SQLite for storage, Blade with Tailwind CSS and Alpine.js on the front end, Vite for the build, and PHPUnit under GitHub Actions.
